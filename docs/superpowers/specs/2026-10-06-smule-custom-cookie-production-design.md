# طراحی سفارش کوکی سفارشی تا دستورکار ERPNext

تاریخ: ۲۰۲۶-۱۰-۰۶

## وضعیت

کاربر مسیر انتقال مواد از انبار مواد به انبار در جریان تولید هنگام ساخت دستورکار را تأیید کرده است. این انتقال با Stock Entry بومی ERPNext انجام می‌شود؛ مصرف نهایی و ورود محصول همچنان با مرحلهٔ بومی `Manufacture` ثبت خواهد شد.

## هدف

مشتری از سازندهٔ فعلی سایت ترکیب کوکی را با مواد منتشرشده از ERPNext انتخاب کند. سفارش ثبت‌شده در `Sales Order` همان Itemهای مواد و مقدار دقیق دستور را نگه دارد. کارمند مجاز بتواند از خود سفارش فروش، برای هر ردیف سفارشی یک `Work Order` بومی بسازد و با تأیید انتقال، مواد همان ردیف را به WIP منتقل کند.

## وضعیت موجود و محدودیت‌های واقعی

- API سفارش سفارشی هم‌اکنون Item خمیر/افزودنی‌ها، وزن و دستور را سرورمحور محاسبه می‌کند و snapshot آن را در فیلدهای `smule_cookie_recipe_*` روی `Sales Order Item` می‌نویسد.
- سازندهٔ سایت هنوز فهرست شناسه‌ها و گزینه‌های اولیهٔ ثابت دارد؛ در خطای API نیز بعضی متن‌ها و محاسبه‌های نمونه در دسترس‌اند. گزینهٔ دلخواه ERPNext هنوز به‌صورت کامل قابل استفاده نیست.
- در اپ `smule_store` هنوز جریان ساخت `BOM`، `Work Order` یا Stock Entry وجود ندارد.
- بررسی ERPNext زندهٔ `boller.ir` نشان داده است که برای تولید، Itemهای مواد اولیه و Warehouseهای مبدا/WIP آماده نیستند. به همین دلیل پیاده‌سازی کد به‌تنهایی اجازهٔ تولید زنده نمی‌دهد و هیچ ماده، BOM، Warehouse یا موجودی‌ای نباید حدس زده یا خودکار ساخته شود.

## معماری و جریان داده

### ۱. سازندهٔ کوکی از ERPNext

- `Item`های فعال و صریحاً منتشرشده با `smule_storefront_type` برابر `Dough`, `Topping` یا `Flavor`، منبع تنها گزینه‌های سازنده هستند.
- `Item.name`/Item Code هویت پایدار هر جزء است؛ slug صرفاً شناسهٔ عمومی UI است و سرور آن را دوباره به Item فعال ERPNext حل می‌کند.
- متن، گروه، وزن افزودنی به ازای بیس ۵۰ گرمی، آلرژن، ارزش غذایی و هزینه فقط از metadata و `Item Price` معتبر ERPNext می‌آیند. مورد بدون اطلاعات لازم برای قیمت‌گذاری/تولید، قابل افزودن به سفارش واقعی نیست.
- خرابی یا خالی بودن API نباید گزینه یا دستور نمونه را به‌جای اطلاعات واقعی نشان دهد. UI فعلی و هویت بصری حفظ می‌شود؛ برای جزء بدون asset اختصاصی از نمایش عمومیِ خنثی استفاده می‌شود، نه نسبت‌دادن تصویر مادهٔ دیگری.

### ۲. ثبت سفارش سفارشی

- سبد فقط پیش‌نویس است. هنگام ثبت، سرور Itemها، انتشارشان، وضعیت نمونه نبودن، مقدارها، UOM، قیمت و مجازبودن سفارش را دوباره بررسی و محاسبه می‌کند.
- سفارش فروش، مرجع اصلی باقی می‌ماند. هر ردیف سفارشی یک Item پایهٔ کوکی، `qty` و snapshot نسخه‌پذیر دستور دارد؛ snapshot شامل Item Code هر ماده و مقدار آن به گرم است.
- مقدار هر ردیف ماده برای یک کوکی چنین است: خمیر = وزن پایه؛ هر افزودنی = مقدار تأییدشدهٔ `smule_grams_per_50g × وزن پایه ÷ 50`. هنگام دستورکار، این مقدار در تعداد Sales Order Item ضرب می‌شود.
- مقادیر snapshot دریافتی از مرورگر مرجع نیستند؛ در checkout سرور آن‌ها را از Itemهای جاری ERPNext محاسبه می‌کند. API ساخت دستورکار فقط snapshot معتبر متصل به Sales Order Item را می‌پذیرد.

### ۳. ساخت دستورکار و اسناد انبار

- روی Sales Order ثبت‌شده، اقدام Desk برای ردیف‌های سفارشی نمایش داده می‌شود. کاربر مجاز ابتدا خلاصهٔ ماده‌ها، مقدار کل و Warehouseهای مبدا و WIP را مرور و سپس صریحاً ساخت را تأیید می‌کند.
- برای هر `Sales Order Item` سفارشی، یک `BOM` فعال و غیرپیش‌فرض مخصوص همان ترکیب ساخته می‌شود. BOM از Item پایهٔ کوکی و ماده‌های snapshot سرور ساخته می‌شود؛ BOM پیش‌فرض یا BOM مشترک Item تغییر نمی‌کند.
- مقدار BOM خروجی برابر یک واحد stock UOM محصول نهایی است. برای هر ماده، تبدیل دقیق مقدار snapshot از `Gram` به stock UOM باید در Item/UOM ERPNext تعریف شده باشد؛ اگر تبدیل دقیق وجود نداشته باشد، عملیات پیش از ثبت متوقف می‌شود.
- سپس یک `Work Order` بومی با `production_item`, BOM و `qty` ردیف سفارش ساخته و به `Sales Order` و دقیقاً همان `Sales Order Item` متصل می‌شود.
- با تأیید ساخت، ERPNext تابع بومی ساخت Stock Entry با purpose=`Material Transfer for Manufacture` را اجرا می‌کند و آن را submit می‌کند. مقدار هر ماده از انبار مواد (source) کم و به WIP منتقل می‌شود. ثبت Manufacture و ورود کالای نهایی، اقدام جداگانهٔ استاندارد ERPNext است.
- محصول ساخته‌شده مقصد نهایی را از `Smule Store Settings.sales_warehouse` می‌گیرد؛ مواد اولیه و WIP تنظیم‌های جدا دارند و از تنظیمات Company/انبار به‌طور حدسی گرفته نمی‌شوند. هر انبار انتخابی باید فعال، برگ و متعلق به Company تنظیم‌شده باشد.
- تکرار درخواست برای همان Sales Order Item باید همان Work Order و Stock Entry موجود را برگرداند و هرگز انتقال دوباره ایجاد نکند. در شکست هر مرحله، transaction باید rollback شود تا BOM/WO/Stock Entry ناقص باقی نماند.

### ۴. اختیار، موجودی و خطا

- endpoint ساخت فقط برای نقش/مجوز تولیدی مجاز و Sales Order با `docstatus=1` قابل اجراست؛ ردیف باید عضو همان سفارش، سفارشی و دارای دستور معتبر باشد.
- پیش از ساخت، موجودی واقعی مواد در Warehouse منبع با مقدار درخواستی و رزروها بررسی می‌شود. کمبود، انبار نامعتبر، Item غیرفعال/غیرstock، UOM ناسازگار، BOM/دستور sample یا ردیف آماده خطای قابل‌فهم می‌دهد و هیچ Stock Entry ثبت نمی‌شود.
- اجرای یک درخواست همزمان یا تکراری باید با بررسی linkهای native و قفل/transaction مناسب idempotent بماند.
- checkout، پرداخت و تحویل آنلاین با این قابلیت خودبه‌خود فعال نمی‌شوند. تنظیم‌های موجود تا تکمیل جداگانهٔ پیکربندی کسب‌وکار خاموش می‌مانند.

## گزینه‌های بررسی‌شده

1. **BOM یکتای هر ردیف سفارش (انتخاب‌شده):** ترکیب آزاد قابل تولید می‌ماند، مقدارها قابل audit هستند و دستور کالای دیگر تغییر نمی‌کند؛ در عوض برای هر سفارش یک سند BOM بومی نگه‌داری می‌شود.
2. **BOMهای دستی برای تمام ترکیب‌ها:** BOMها مرتب و قابل استفادهٔ مجددند، اما ترکیب آزاد به فهرست محدود BOMهای ازپیش‌تعریف‌شده تبدیل می‌شود و با سازندهٔ فعلی سازگار نیست.
3. **کسر موجودی با API/SQL سفارشی:** انتخاب نمی‌شود؛ موجودی/دفترکل ERPNext را دور می‌زند و اسناد native و audit را ناقص می‌کند.

## محدودهٔ پیاده‌سازی

### داخل محدوده

- گزینه‌ها و محاسبات UI بر پایهٔ کاتالوگ زندهٔ اجزای ERPNext و حذف fallback نمونه در سازندهٔ سفارش.
- snapshot دقیق و قابل اعتبارسنجی در `Sales Order Item`.
- تنظیم و اعتبارسنجی Warehouse مواد و WIP، جدا از Warehouse محصول نهایی.
- اقدام Desk با preview/confirmation، ساخت BOM اختصاصی، Work Order و Stock Entry استاندارد، مجوز، idempotency و کنترل کمبود.
- unit/API tests و build/smoke test بدون تغییر Item یا موجودی زنده.

### خارج از محدوده

- ساخت یا نگاشت خودکار Itemهای مواد اولیه از نام‌های ثابت فعلی؛ مدیر باید Item Code، stock UOM، conversion factor، قیمت و metadata واقعی را در ERPNext تعریف/تأیید کند.
- تولید یا submit کردن خودکار Stock Entry `Manufacture`؛ تکمیل ساخت و ورود محصول بعد از دستورکار از گردش عادی ERPNext انجام می‌شود.
- تغییر سفارش‌های قبلی، موجودی، تنظیمات درگاه، فعال‌سازی checkout، ایجاد Warehouse یا انتشار خودکار کالاها.

## آزمون و معیار پذیرش

1. UI همهٔ Dough/Topping/Flavorهای live با slug دلخواه را می‌خواند؛ خطای API یا پاسخ خالی هیچ دستور نمونه/قیمت جعلی نمایش نمی‌دهد و سفارش را نمی‌پذیرد.
2. checkout مقدار هر ماده را در سمت سرور محاسبه و در snapshot ردیف Sales Order ذخیره می‌کند؛ تغییر payload سمت مرورگر نمی‌تواند Item یا مقدار مواد را جعل کند.
3. preview سفارش همان مقدارهای قابل audit را برای `qty` کل نشان می‌دهد.
4. ساخت دستورکار، BOM فعال و غیرپیش‌فرض می‌سازد، Work Order را به SO و SO Item درست وصل می‌کند و از endpoint بومی ERPNext برای Stock Entry استفاده می‌کند.
5. submit موفق Material Transfer موجودی source را دقیقاً به مقدار BOM × تعداد کاهش و WIP را همان‌قدر افزایش می‌دهد؛ هیچ مصرفی از itemهای غیرانتخاب‌شده رخ نمی‌دهد.
6. کمبود stock، نبود Warehouse، تبدیل UOM ناموجود، BOM نامعتبر، SO ثبت‌نشده و درخواست تکراری پیش‌بینی‌شده‌اند؛ هیچ کدام باعث مصرف مضاعف یا دادهٔ ناقص نمی‌شوند.
7. تست‌ها با fixture/mocks ایزوله اجرا می‌شوند؛ هیچ Item، BOM، Warehouse، Work Order، Stock Entry یا Bin زنده‌ای توسط تست تغییر نمی‌کند.
8. در سایت زنده، قابلیت تا زمان آماده‌شدن مواد، انبارها، قیمت‌ها و مجوزها صرفاً کد می‌ماند و تولید یا checkout به‌طور ضمنی روشن نمی‌شود.
